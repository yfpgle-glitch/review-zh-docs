# 文档类型检查与改写模式

仅在需要文档类型检查清单或具体改写参照时读取本文件。先使用 `SKILL.md` 的核心流程，不要把这里的条目机械套进每份文档。

## 需求文档 / PRD

检查是否写清：

- 用户角色和触发场景
- 输入、输出和状态变化
- 权限、异常和重复操作
- 成功标准和失败条件
- 本轮非目标

只有“支持上传文件”不够。至少需要确认文件类型、大小限制、重复上传规则、失败处理和权限边界；材料没有提供时，将缺项列为待确认，不自行设计。

## README / 项目说明

检查是否写清：

- 项目是什么，以及明确不包含什么
- 安装、运行、构建和测试命令
- 必需环境、依赖和配置项
- 入口目录与关键文件
- 常见限制和新人下一步

从项目清单文件、脚本和现役配置核对命令。不要用“现代化技术栈、易于维护”代替可执行信息。

## 技术方案 / 架构方案

检查是否写清：

- 当前问题、约束和目标
- 方案选择及依据
- 主要备选方案和放弃原因
- 数据流、调用链和模块边界
- 依赖、兼容性、风险和回滚
- 测试方法和验收方式

“采用服务端实现以提升稳定性”没有提供取舍。应说明哪些操作放到服务端、它解决什么具体风险，以及仍未确认的约束。

## 实施计划 / 路线图

检查是否写清：

- 前置条件和任务顺序
- 每步输入、输出和完成标准
- 阻塞条件与负责人（材料提供时）
- 可以并行和必须串行的事项
- 当前下一步

不要把“持续优化、逐步完善”当成任务。每一项应能判断是否完成。

## 周报 / 复盘 / 总结

检查是否写清：

- 已完成的具体产物
- 已验证和未验证的内容
- 发现的问题及其影响
- 未完成事项和下一步
- 数据、日期和结论的来源

将“显著提升、全面优化、奠定基础”替换为页面、接口、文档、脚本、数据或验证结果；没有事实时删除，不补写。

## 通用改写模式

### 空话改为事实或待确认项

改前：

> 本项目旨在全面提升用户体验和系统能力。

有来源时，写清当前问题、本轮范围和非目标。没有来源时改为：

> 待确认：当前问题、本轮要解决的范围、目标用户以及明确不包含的内容。

### 抽象动作改为可验收要求

改前：

> - 优化用户体验
> - 完善数据管理

不要自行创造功能。先从材料确认对象、行为和成功标准；确认不了时列出缺失项，而不是换一组更正式的形容词。

### 冗长表格改为合适结构

- 多个对象使用相同字段比较时保留表格。
- 单元格里是完整段落时改为小节或列表。
- 标题下只有一句话时，优先并回正文，不制造空层级。
